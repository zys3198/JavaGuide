去年我给一个内部 Agent 项目做记忆，上了一套完整的向量检索链路（Qdrant + embedding + reranker），部署就折腾了三天。结果跑了两周，团队反馈最多的一句话是"它记了一堆没用的，真正该记的一个没记住"。后来我试着把记忆改成几个 Markdown 文件手动维护，效果反而好了不少。当时觉得挺讽刺的。

直到我仔细看了 Claude Code 的记忆系统实现，才发现这不是巧合。它没用向量数据库、没用 embedding，整套记忆就是靠结构化的 Markdown 文件加一个小模型当选择器跑起来的。而且跑得比大多数向量检索方案都稳。

这篇文章把 Claude Code 的记忆设计拆开讲。全文接近 8000 字，建议收藏，主要看这几块：

1. LLM 本身没有记忆，记忆机制要解决什么问题
2. Claude Code 的两层记忆架构：静态层和动态层
3. 静态层 CLAUDE.md 的六个层级怎么分工
4. 动态层 Auto Memory 的完整闭环：四种类型、写入、索引、检索、老化
5. 多 Agent 场景下记忆怎么共享
6. 这套方案和向量检索各自适合什么场景
7. 能直接用到自己项目里的几条设计原则

## LLM 没有记忆，那对话是怎么连续的？

先快速过一遍底层事实。

LLM 的推理过程没有任何跨请求的状态保留。每次调用，你看到的是一条消息进去、一条回复出来，但背后是把系统提示词、完整对话历史和当前问题打包成一个大输入喂给模型。模型不记得"上一次"做了什么，它只看当前这一包数据。ChatGPT 聊到第 50 轮还"记得"你说过的话，是客户端在重发历史消息，不是模型有记忆。上下文窗口就是这个数据包的体积上限。

聊天场景下这套还能撑住。Agent 模式不行。Agent 一旦进入连续操作链（调工具、读文件、执行命令），上下文增长速度远超"你一句我一句"的聊天。几个回合下来窗口就见底了。

更关键的是，Agent 需要持久化的信息跟对话历史性质不同。你昨天跟 Agent 说过一句"不要用 mock 测试"，今天开新会话，你希望它直接照做，而不是你再说一遍。这种"规则类"的信息，它的生命周期跨越单次对话，跟"你昨天说了什么话"是两码事。

所以 Agent 记忆要解决的本质问题是：跨会话保留哪些信息、用什么结构存储、如何判断一条记忆是否还有效、以及谁来执行写入和清理。Claude Code 给出了一个挺出乎意料的答案。

## Claude Code 的两层记忆架构

Claude Code 的记忆分两条独立的线，并行工作。

**静态层是 CLAUDE.md 体系**，你可以把它理解为项目级配置文件。开发者预先写好规则和约束，Agent 每次启动都会全量读取。核心解决的问题是协作规范和项目约束，这类信息是确定的，不需要 Agent 去猜。

**动态层是 Auto Memory**，这部分由 Agent 自主维护。在协作过程中，Agent 会根据用户的反馈、纠正和偏好，自动把有价值的经验写入磁盘，后续会话再根据当前任务按需加载。核心解决的是经验沉淀，这类信息是随协作过程逐步积累的，开发者事先无法预料。

换个角度理解：静态层是项目启动前你就摆好的规矩，Agent 一来就照着走，属于"预设知识"；动态层是 Agent 在和你协作过程中自己沉淀的经验，属于"习得知识"。前者处理确定性（"这个项目要遵守什么"），后者处理不确定性（"我从跟你的互动中学到了什么"）。

Claude Code 官方文档对这两层的定位很明确：

> CLAUDE.md files: instructions you write to give Claude persistent context
> Auto memory: notes Claude writes itself based on your corrections and preferences

| 维度 | CLAUDE.md（静态层） | Auto Memory（动态层） |
|------|---------------------|----------------------|
| 谁写 | 你 | Claude 自己 |
| 内容 | 指令和规则 | 学到的偏好和经验 |
| 加载时机 | 每次会话启动时全量加载 | 每次会话启动时加载索引，内容按需加载 |
| 适合存 | 编码规范、工作流、项目架构 | 构建命令、调试经验、用户偏好 |

两层一起用，才是完整答案。接下来分别展开。

## 静态层：CLAUDE.md 的六个层级

很多人对 CLAUDE.md 的印象停留在"项目根目录放一个 md 文件"。但 Claude Code 的 CLAUDE.md 体系远比这复杂。

### 为什么不能只有一个 CLAUDE.md

如果只有一个 CLAUDE.md，你很快会发现想往里塞的"规则"根本不是同一个来源。公司级的强制策略（"禁止 commit secrets"）得全员生效；你个人的习惯（"commit message 用中文"）希望跨所有项目通用；项目自己的规则要签入 Git 给团队共享；本地调试用的约定不想签入 Git。

这六种来源，可见范围不同、谁能改也不同，硬塞进一个文件只会打架或者混乱。所以 Claude Code 把它拆成了六个层级。

### 六个层级各管一摊

按加载顺序从低到高：

| 层级 | 位置 | 作用范围 | 适用场景 |
|------|------|----------|----------|
| **Managed** | 系统级路径（如 Windows 的 `C:\Program Files\ClaudeCode\CLAUDE.md`） | 组织内所有用户 | 公司编码规范、安全策略 |
| **User** | `~/.claude/CLAUDE.md` | 个人所有项目 | 代码风格偏好、个人工具习惯 |
| **Project** | `./CLAUDE.md` 或 `./.claude/CLAUDE.md` | 团队共享 | 项目架构、编码标准，提交至 Git |
| **Local** | `./CLAUDE.local.md` | 个人当前项目 | 沙箱 URL、测试数据偏好，加入 `.gitignore` |
| **Auto** | `~/.claude/projects/<project>/memory/` | 项目级，跨 worktree | Claude 自动写入的偏好和经验 |
| **Team** | Auto 目录下的 `team/` 子目录 | 团队共享 | 团队共同积累的 AI 学习偏好 |

六层之间是叠加关系，不是覆盖关系。Claude Code 启动时把它们全部拼接进上下文，让模型一起看到。越靠近工作目录的规则优先级越高。

加载机制有个细节值得注意：Claude Code 从当前工作目录逐级向上查找。同一目录内，`CLAUDE.local.md` 追加在 `CLAUDE.md` 之后。子目录下的 CLAUDE.md 不会在启动时全量加载，而是 Claude 读取该子目录文件时按需加载。

### 条件规则：编辑 .tsx 才加载前端规范

光分层还不够。假设你有一份几百行的前端规范，但只在编辑 `.tsx` 文件时才需要，编辑后端代码加载它就是浪费 token。

Claude Code 在 `.claude/rules/` 目录下支持条件规则。每条规则是一个独立的 md 文件，frontmatter（文件开头的元数据区）里用 `paths` 字段做 glob（文件路径匹配模式）匹配：

```yaml
---
paths:
  - "src/api/**/*.ts"
---

# Controller 规范
- 统一使用 Result<T> 包装返回值
- 所有接口必须添加 Swagger 注解
```

只有编辑匹配路径的文件时，这条规则才会加载进上下文。这个设计的核心价值是：**规则不再是"一次性全塞"，而是按需注入**。大项目可以有几十条规则，每条只在需要时才占 token。

### 文件引用：@import 机制

CLAUDE.md 文件可以用 `@path/to/file` 语法引用外部文件。引用文件在启动时全量展开加载，和直接写在 CLAUDE.md 里效果一样。最多支持 4 层递归深度。

要注意的是，`@` 引用能改善组织结构，但不会减少上下文消耗，被引用的文件在启动时全量加载。如果指令很长，优先用 `.claude/rules/` 的 path-scoped rules 做按需加载，而不是用 `@` 拆分。

### AGENTS.md 兼容

Claude Code 读的是 `CLAUDE.md`，不是 `AGENTS.md`。如果仓库已经用 `AGENTS.md` 给其他编码 Agent 提供指令，可以创建一个导入 `AGENTS.md` 的 `CLAUDE.md`：

```markdown
@AGENTS.md

## Claude Code 特定指令

- 使用 plan mode 处理 `src/billing/` 下的改动
```

这样两个工具复用同一份基础指令，不用重复维护。

## 动态层：Auto Memory 的完整闭环

静态层再完善，也有一个根本局限：**所有内容都依赖开发者手动维护**。你在某次对话中纠正了 Agent 的做法，比如"集成测试必须连真实数据库"，下一次新会话里它还是可能犯同样的错，因为你没把这条规则写到 CLAUDE.md 里。Auto Memory 就是来弥补这个缺口的，让 Agent 在协作过程中自主识别值得持久化的经验，自动写入、自动检索。

### 四种封闭式记忆类型

要让 Agent 自己写记忆，第一个问题是：让它写什么？

如果放任自由发挥，它一天能写出"用户今天的项目是 Spring Boot"（当前会话信息，下次没意义）、"这个文件有 200 行"（文件系统里的统计值）、"上一次任务改了 3 个文件"（活动日志，对后续决策无用）……几天下来记忆库就成了什么都查不准的垃圾桶。

Claude Code 的做法是划定一个极窄的分类边界：**记忆只能属于四种预定义类别之一，其余内容不允许写入持久化存储**。

为什么必须是闭合系统，而不是允许自定义类型？理论上自由分类更灵活，但实践中 Agent 会在不同上下文里创造出五花八门的标签，比如"调试偏好""代码风格""团队约定""性能笔记"，同一条信息可能被归到好几个类别下。时间一长，分类体系膨胀，检索时 Agent 不知道该去哪个类别里找，每次对话开头都要花更多 token 理解这些混乱的标签。

四类型的做法是刻意收窄分类空间。写之前必须先回答一个问题：这条信息讲的是人、是规则、是项目状态、还是外部链接？回答清楚才能落笔。分类简单了，检索和推理效率都跟着提升。

| 类型 | 记什么 | 典型内容 |
|------|--------|----------|
| **user** | 用户是谁、擅长什么、知识水平 | "写了十年 Go，刚接触 React" |
| **feedback** | 用户不喜欢什么、确认有效的做法 | "不要用 mock 测试，要打真实数据库" |
| **project** | 项目正在发生什么 | "移动端 3 月 5 号开始合并冻结" |
| **reference** | 去哪查什么 | "pipeline bug 在 Linear 的 INGEST 项目里追踪" |

其中 `feedback` 和 `project` 有强制结构，正文必须包含：

```markdown
规则本身

**Why:** 用户为什么这么要求（往往是踩过的坑）
**How to apply:** 什么情况下生效
```

只记规则不记原因，遇到边界情况就抓瞎。比如"不要用 mock 测试"，单纯一句话不够。加上"上季度 mock 测试通过但 prod 迁移挂了"这个 Why，Agent 在边界情况下就能自己判断该不该破例。

`project` 还有个要求：**必须把相对日期转成绝对日期**。用户说"周四之前冻结"，存进去要变成"2026-03-05 之前冻结"。"周四"过几天就过期了，绝对日期永远准确。

### 不该存什么

跟"该存什么"同样重要的是"不该存什么"。Claude Code 明确列了禁令：

- 代码模式、架构、文件路径：代码里 grep 一下就有，存了反而和实际状态不一致
- Git 历史和最近改动：`git log` 是权威，记忆只会落后于真相
- 调试方案和修复方法：fix 在代码里，context 在 commit message 里
- CLAUDE.md 里已经写过的内容：重复占空间
- 临时任务状态和当前对话上下文：变化太快

核心原则就一条：**只记代码推不出来的东西**。代码库是持续变化的真实来源，而记忆一旦写入就变成了某个时刻的快照。一条过时的记忆比没有记忆还糟糕，因为 Agent 会把它当真理。

### 存储设计：MEMORY.md 索引 + 独立文件

每条记忆是一个独立的 `.md` 文件，带 YAML frontmatter：

```yaml
---
name: feedback-no-mock
description: 集成测试必须连真实数据库，不用 mock
metadata:
  type: feedback
---

集成测试必须连真实数据库，不要用 mock。

**Why:** 上季度 mock 测试通过了但 prod 迁移挂了
**How to apply:** 所有标了"集成测试"的 case 都适用
```

所有记忆文件放在 `~/.claude/projects/<project>/memory/` 目录下。目录里有一个特殊的 `MEMORY.md` 文件，是所有记忆的索引清单。

这里有个关键设计决策：**索引和正文分离加载**。

`MEMORY.md` 索引始终加载进上下文（让 Agent 知道有哪些记忆可选），完整内容按需加载（不浪费 token）。这和数据库系统里的"B+ 树索引 + 回表查询"思路异曲同工，索引页常驻内存，数据页按需从磁盘加载。Agent 看到索引中的 name 和 description，就知道有哪些记忆可供选择；真正需要某条的完整内容时，再去读取对应的文件。

`MEMORY.md` 有严格的容量控制，前 200 行或 25KB（先到者为准），超出部分不会加载。Claude Code 还用了行数 + 字节的双保险截断，防止"一行超长字符串撑爆上下文"这种极端情况。源码里能看到这个防护：

```text
MAX_ENTRYPOINT_LINES = 200
MAX_ENTRYPOINT_BYTES = 25_000
```

两个限制任意一个先触发就截断，并追加一条警告告诉模型"索引被截过了，部分内容没加载"。

### 写入：后台代理抽取

记忆是怎么写进去的？最直觉的做法是让主对话每轮结束后自己写，但有两个坑：模型分心（主任务和记忆抽取抢注意力）、token 浪费（每轮都要塞一段"记一下偏好"的指令）。

Claude Code 的方案是：**每轮对话结束后，后台单独跑一个代理来抽取记忆**。这个代理叫 `extractMemories`，触发时机是主对话完整结束（模型给出最终回复、没有 tool call 了）。

这个后台代理不需要冷启动。它直接继承主对话的完整上下文状态，包括已经缓存好的提示词。系统提示词、工具定义这些固定内容不需要重新发送，后台代理只需扫描对话历史，判断"有没有值得持久化的信息"。整个抽取过程额外消耗的 token 很少。

缓存共享能省多少？简单算一笔账。系统提示 + 工具定义 + 对话历史，一个中等长度的会话轻松到 80000 token。如果后台代理从零加载，这笔钱得重新付一遍。有缓存共享的话，因为前缀完全相同，API 只收缓存读取的费用，成本降了一个数量级。频繁使用 Agent 的场景（每天几十次对话），这个差额累积起来很可观。

缓存共享有一个隐含约束：**工具列表是 API 缓存 key 的一部分**。如果 fork 出来的代理使用不同的工具集，缓存就无法命中。Claude Code 的做法是给后台代理传一份相同的工具列表，但在运行时通过回调函数拦截：只读工具放行，写入类工具只允许往记忆目录里写，其余一律拒绝。工具定义不变，缓存能命中；行为在执行时按需过滤。这个架构技巧值得记：定义层保持一致，控制层区分行为。

后台代理的权限很严格：只读工具（Read、Grep、Glob）不受限制；Bash 只允许只读命令（ls、find、grep）；Edit/Write 只能写记忆目录内的路径；其他所有工具一律拒绝。后台代理能看到项目代码，但不能改。

抽取代理会做几件事：扫一遍对话里用户的反馈和纠正；跟现有记忆比对避免重复；按四种类型分类写入新文件。

这里还有一个**互斥机制**：如果主 Agent 已经在本次对话中主动写入了记忆，后台抽取会检测到并直接跳过。两边的写入是互斥的，谁先动，另一边就歇着。不然的话，同一次对话产生的同一条偏好，可能被主 Agent 和后台代理各写一份，占用双倍空间不说，检索时还得做去重。

### 节流与尾随提取

记忆提取不是每次对话都跑。系统有基于计数器的节流机制：每积累若干轮对话后才触发一次提取。成本考量很直接，每次提取都需要一次 API 调用，频繁的短对话（简单问答）提取记忆的成本可能超过价值。节流确保了每次提取的"信息密度"够高。

但节流会带来一个并发问题：如果提取正在进行时有新对话完成，新对话的上下文可能永远不被提取。系统用 **trailing extraction（尾随提取）** 解决了这个问题。新对话的上下文先暂存，当前提取完成后，用最新暂存的上下文跑一次尾随提取。尾随提取跳过节流计数器，它处理的是已经完成的工作，不该被节流延迟。

### 检索：用 Sonnet 当选择器

下次对话来的时候，假设有 100 条记忆，怎么挑出最相关的几条？

Claude Code 偏偏不用向量检索。它的做法是让一个小模型来选，整个过程可以概括为三步。

先是**收集候选**：遍历所有记忆文件的元数据区域（只读文件开头部分，不读完整内容），收集每条记忆的标题和摘要。

然后是**构造提示**：把这些摘要信息组织成一份候选清单，连同用户当前的问题一起提交给 Sonnet：

```text
Query: 用户当前的问题

Available memories:
- user_role.md — 后端工程师，新接触 React
- feedback_no_mock.md — 测试不要用 mock
- project_freeze.md — 3 月 5 号开始合并冻结
...
```

最后是**结构化输出**：要求 Sonnet 严格按照预定义的 JSON 格式返回它认为最相关的若干条记忆的文件名。系统提示词强调"拿不准的就不选"，宁可漏选也不要误选。

为什么用 Sonnet 不用更便宜的 Haiku？因为记忆相关性判错的代价远大于多花的那点 token。一旦把错的记忆塞进上下文，整个回复都会被污染。这道选择题的容错率非常低。

检索环节还有两个过滤策略值得说。其一，已经在当前对话中使用过的记忆不会重复加载，把有限的注入名额留给还没出现过的候选。其二，正在使用的工具的操作手册类记忆不加载（Agent 已经在实际操作了，再塞文档就是噪音），但跟这些工具相关的"踩坑警告"和"已知问题"会保留，恰好在使用某个工具的时候，跟它相关的警告才是最有价值的。

### 注入：老化警告 + 主动验证

记忆选出后，Claude Code 通过特殊的系统标签把它注入对话上下文，和用户消息明确分隔，防止模型混淆信息来源。

注入时附带**时效性标记**：

```text
This memory was saved 5 days ago. Verify it's still accurate before acting on it.
```

2 天以前的记忆，Claude Code 会主动加上"可能已过时"的提醒。软件开发节奏快，两天前的"项目正在做 X"可能今天已经改了。模型收到这类记忆时，会带着"这是历史记录，不是当前状态"的心态去参考。

Claude Code 还有一段提示词，专门指导模型如何对待记忆中的事实：

> 一条过时的记忆不能当作当前事实。记忆提到某个文件路径，要先确认文件是否还在；记忆提到某个函数或配置项，要先在代码库中搜索确认；当用户要基于记忆中的建议采取行动时，必须先验证再执行。

这种设计本质上是在定义一个信任梯度。一端是完全不信任记忆，每次都重新获取，记忆系统白做了。另一端是盲信记忆，代码库变了也不知道。Claude Code 选了中间位置：记忆是参考线索，不是权威结论。它告诉你"大概是什么情况"，但使用前必须和当前代码库对齐。

有个维度值得注意：记忆的类型决定了信任的合理程度。决策背景类（"选择 PostgreSQL 是因为需要复杂查询"）解释的是"为什么"而非"是什么"，不太会过时，可以直接信。文件路径类（"用户认证在 `src/auth/handler.ts` 中"）可能在重构后变了，必须先查。

## 多 Agent 场景下的记忆共享

单个 Agent 的记忆是自己的事。但当多个 Agent 需要协作时，记忆怎么共享？

Claude Code 的做法是在 Agent 团队里引入基于文件的通信机制。每个 Agent 有一个以自己名字命名的 JSONL（JSON Lines，每行一条 JSON 记录的文本格式）文件作为消息队列，新消息追加到文件末尾，读取时一次性取出所有内容并清空文件（即"读后即焚"模式）。

```text
.team/
  config.json       ← 团队成员注册表 + 状态信息
  inbox/
    alice.jsonl      ← 追加写入，读后清空
    bob.jsonl
    lead.jsonl
```

通信接口只有两个操作：往目标收件箱追加一条 JSON 格式的消息，以及从自己的收件箱读取全部消息并清空。每次模型推理前，Agent 都会先轮询自己的收件箱，有新消息就注入当轮上下文。

`config.json` 维护团队成员信息和状态。每个 Agent 的生命周期不是一次性销毁的，而是可以反复在"接到任务时工作、空闲时待命"之间切换，直到被显式终止。Leader Agent 可以随时创建新队友，队友之间通过收件箱互相传递消息。整个通信过程是结构化的、可审计的，打开 JSONL 文件就能看到完整的消息历史，出问题时追踪单条消息的来源很直接。

## Markdown 记忆和向量检索怎么选？

Claude Code 这套方案看完了，一个自然的问题是：它和向量检索到底各自适合什么场景？

| 维度 | Markdown + LLM 选择 | 向量检索 |
|------|---------------------|----------|
| 检索精度 | 高（模型理解语义和上下文） | 中高（相似不等于相关） |
| 上下文成本 | 索引常驻，按需加载 | 按需检索，上下文高效 |
| 调试体验 | 极佳，打开文件就能看 | 中等，需要向量查询工具 |
| 部署成本 | 极低，只需文件读写 | 高，需维护向量服务 |
| 适合的记忆量 | 几十条到几百条 | 几万条到几十万条 |
| 可解释性 | 强（能看到选择依据） | 弱（相似度分数难解释） |

Claude Code 选择 Markdown 方案的核心原因是：**Agent 记忆的数量级通常在几十到几百条**，远没到需要向量检索的规模。在这个量级下，用一个小模型当选择器，精度比向量检索高，成本比向量检索低，调试体验好得多。

但如果你的场景是从几十万条非结构化文本里检索特定片段，向量检索的语义检索能力不可替代。两者不是二选一，而是各有适用边界。

## 能直接抄走的几条设计原则

看完 Claude Code 的整套实现，有几条原则可以直接用到自己的 Agent 项目里。

**写入前先分类，别让记忆变成垃圾桶。** 不加约束的记忆存储很快会退化成无结构的文本堆。给记忆定一个 schema，哪怕只有 4 个字段（type、name、description、content），写入质量就会发生质变。强制分类的本质是在写入前加一道"这条信息到底属于哪一类"的决策门槛，过滤掉模糊和不确定的内容。

**轻量索引常驻，完整内容延迟加载。** 任何"总量大但每次只用少量"的信息场景都适用：长 RAG 文档、知识库、工具描述列表、历史 PR 摘要……都可以拆成"轻量索引常驻上下文 + 完整内容按需展开"。

**相关性判断交给模型，别依赖数值阈值。** 只要候选集合在几百条以内，让语言模型直接挑选比计算向量相似度更准确。向量相似度返回的是一个 0 到 1 的分数，但"0.87 分算不算相关"需要人工定阈值，而这个阈值极难调。让模型选择，返回的是"选/不选"的语义判断，调试和迭代都比调阈值直观。

**给记忆加保质期，用之前先对账。** 记忆不是实时数据，是某个时刻的快照。Claude Code 对超过 2 天的记忆附加过期提醒，使用前要求模型验证关键事实。这个思路可以概括为：存进去的信息要标时间戳，用之前要和当前状态对账。

**写入要克制。** 该不该存比怎么查更重要。只存代码推不出来的东西：用户偏好、项目约定、踩坑记录、外部指针。代码里能 grep 到的、Git 历史里能查到的、CLAUDE.md 里已经写过的，一律不存。

## 记忆管理的三个常见误区

看完设计原则，再列几个实际使用中容易踩的坑。

| 误区 | 典型表现 | 正确做法 |
|------|----------|----------|
| 记忆越多越好 | MEMORY.md 膨胀到几十条，低价值文件堆积 | 删掉这条后 Agent 行为会变吗？不会就不该存 |
| 把记忆当文档库 | 让 Agent 记住技术规范和设计文档 | 放 `docs/` 目录，记忆只存"为什么选 X"不存"X 是什么" |
| 不处理相对日期 | "下周二上线"原样保存，几天后变成错误信息 | 凡是涉及时间，必须存成绝对日期 |

**误区一展开说**：刚开始用的时候，很多人恨不得让 Agent 记住对话里的每个细节。结果 Agent 每次开局要花更多 token 去筛这些噪音，反而可能忽略真正重要的几条。

**误区二展开说**：技术规范和设计文档放 `docs/` 目录更合适，Agent 随时能读到。记忆系统该存的是架构决策背后的原因，不是架构本身。

**误区三展开说**：用户说"下周二上线"，Agent 原样保存。两天后新对话里，"下周二"已经不是同一个日期了。一周后这条记忆直接变成错误信息。
